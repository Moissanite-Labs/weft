## What we are building

The recurring author intent is an environment in which people can shape useful software and intelligence continuously: models act as specialist cells, cells have bounded lifecycles and feedback, applications can adapt around an individual's intent, and the interface makes the system understandable and directly manipulable. Program state, human control, provenance and resource costs remain visible as the implementation grows from commodity machines toward new computation substrates. Biological names preserve the ambition and design language; experiments establish which mechanisms work.

This is a family of connected systems, with several independently useful products. The original prompts support starting with a proof of concept on an existing OS, preserving measurable evidence, and challenging premature completion claims. They also explicitly explore a token-free branch, a unified proof/execution language, shared design fragments and education through interactive explanation. None should disappear merely because the present repository happens to contain a Python harness and Solidity contracts. See the source-reader notes for exact turn/line evidence: [genesis/design](https://github.com/Moissanite-Labs/weft-loom/blob/main/audit/notes-threads_design.md), [main thread](https://github.com/Moissanite-Labs/weft-loom/blob/main/audit/notes-thread1.md), [standalone corpus](https://github.com/Moissanite-Labs/weft-loom/blob/main/audit/notes-top_corpus.md), [design/supplement](https://github.com/Moissanite-Labs/weft-loom/blob/main/audit/notes-supplement_design.md).

The first useful integrated demonstration should be small: **a local knowledge workspace with a procedural, accessible interface, explicit human intent, a bounded adaptation experiment, an inspectable evaluation record and one-step rollback**. It must work with the model disabled and without a ledger. This is a proposed comparison application, chosen because it exercises several source ideas with one observable user task; it is not a claim that the author selected a final product or that a self-evolving OS already exists.

## Preserve the source's distinct forms of evolution

| Mechanism | Changes | Baseline / deciding evidence | Relationship |
|---|---|---|---|
| Aesthetic interpolation | Layout/style parameters within a fixed design vocabulary | Same information and task, accessible controls, stable text, measured render cost | Useful procedural web tooling now; does not require learning |
| Model-responsive presentation | A classifier's bounded presentation decisions | Frozen layout and existing heuristic on held-out interactions | Local inference experiment; model execution is not online training |
| Weight adaptation / mitosis | Candidate parameters of a model/cell | Frozen model, single candidate, random choice and paired candidate selection on the same task | C1 experiment; norm bounds constrain parameters, not all behavior |
| Graph-program evolution | Net structure and rewrite/execution rules | Precisely stated language, valid-net checker and reference reducer | C3/compiler research; independent of Torch tensor adaptation |
| Intent-driven application composition | Components/workflows selected or assembled to satisfy a task | Fixed application and explicit intent/permission/evaluation contract | Product experiment; requires meaningful user outcomes and rollback |
| Morphogenetic interface | Spatial rules/state; potentially learned update weights | Fixed layout, hand-authored cellular rules and trained NCA compared separately | Current widget is a demonstration; learned persistence/repair is a separate experiment |
| Social/institutional evolution | Allocation rules, roles, consent and dispute procedures | Tabletop cases, participant agreement, appeals and outcome measurements | Governance research and eventual adoption; code cannot supply legitimacy |

No single implementation of one row establishes another. Where useful, they share telemetry, evaluation records, identity and explicit interfaces. The [source ledgers](https://github.com/Moissanite-Labs/weft-loom/blob/main/audit/README.md) retain versions that use different mechanisms under similar names.

## Two coordinates for every work item

Keep the principal's six **tracks**: procedural mathematical web; model-responsive web; evolving applications; OS embodiment; custom hardware/Terrafab; governance. C1–C3 and telemetry are shared foundations. Assign each item a **maturity phase** below as well. This prevents a future chip from blocking today's interface, or a local contract test from being mistaken for societal readiness.

| Phase | Deliverable and exit gate | What can start in parallel | Horizon on the reported M1/64 GB + Chrome target |
|---|---|---|---|
| **P0 — Recover and make claims inspectable** | Immutable inventory, substantive file records, variants, contradictions, dependencies, work log and clean resume instructions. No unaccounted baseline file. | Source-backed research briefs and small reproduced repairs | Now; no specialized hardware. This audit establishes the reading baseline, not universal semantic correctness. |
| **P1 — Make current components trustworthy** | Correct wire/state contracts, passing failure tests, reproducible dependencies and truthful outputs. Each advertised capability identifies implementation and evidence. | C1/C2/C3 repairs, telemetry/browser work, local EVM verification, docs correction | Current CPU/browser development. Mac-specific claims await actual Mac results. Small fixes can be individual iterations; language/policy decisions may take longer. |
| **P2 — Deliver independent useful tools** | A clean-checkout local kit, accessible procedural browser demo, explicit configuration, second consumer for reusable modules, reproducible result records. | Teaching widgets, theme import/export, native CPU/MPS measurements and local contract tools | Near-term engineering after relevant P1 gates; scoped packages fit days to weeks, not a commitment to finish the entire phase in that time. |
| **P3 — Test bounded adaptation** | One task per experiment with baseline, held-out evaluation, bounded resources, recorded failures and a continue/stop decision. | Laya, cell selection, personal preferences, NCA, application composition, token-free resource feedback | Small experiments can begin now; usefulness and scaling are unproven. Download size, browser buffer limits, latency and thermals remain separate from total RAM. |
| **P4 — Compose and verify systems** | Versioned component integration, deterministic replay where applicable, isolation/recovery, provenance binding and consented local federation. Proof work has an explicit implementation correspondence statement. | Compiler/reference semantics, single-host multi-process cells, local permissioned protocol tests, governance simulations | More sustained engineering/research. FPGA boards, lab access, native GPU kernels and toolchain support need specific resources and measurements. |
| **P6 — Commit external resources and institutions** | A reviewed foundry/packaging/energy/cost case, or an adopted governance pilot with authority, consent and appeal. Independent decision for each branch. | Partnerships, economic research and small consensual pilots where authorized | No date supported by this corpus. These are advancement criteria, not a waterfall. A P3 experiment may expose a new P1 defect. A rejected experiment is a durable result, not a reason to remove its source branch.

## Integration contracts that prevent premature coupling

| Contract | What must be fixed before dependent work |
|---|---|
| I1 telemetry frame | Version, widths/endian/units, slot meaning, provenance carrier, unavailable values, atomic update and consumption. A 64B frame is one input, not the whole renderer state. |
| I2 symbolic packets | Grammar, digest coverage, sequence/replay/freshness semantics and producer/consumer vectors. Payload integrity does not authenticate a publisher. |
| I3 numerical gate | Explicit policy profile, input domain/shape/precision, overflow/nonfinite rules, inclusive boundaries and rejection-state effects. |
| I4 memory arena | Layout identity, ownership, attach/version compatibility, synchronization and teardown. Shared CPU views do not prove device zero-copy or sandboxing. |
| I5 graph/trace | Separate graph encoding, live checkpoint and execution trace. Define port identity, valid graph, failure semantics and canonical bytes. |
| I6 ledger | Generated ABI/events plus differential local-EVM vectors and explicit authority/revert semantics. |
| I7 provenance | Artifact serialization, claimed relationship, signer/evidence, revocation/contest and threat model. No automatic equivalence between hash, watermark and ownership. |
| Proposed intent/evaluation contract | Task, allowed changes, protected state, baseline, evaluation budget, accepted evidence, promotion and rollback. Draft before a general app compiler. |
| Proposed whole-runtime journal/result contract | Initial state, actual inputs/RNG/configuration, effective backend/model versions, candidate/committed identities, authorizations, timestamps, nondeterminism/tolerances and retrievable artifacts. Use before P3 adaptation; graph/weight hashes are only part of it. |
| Proposed theme/spatial-state contract | Tokens/units/schema/version, stable identity, compatible rendering targets, accessible fallback, local import/export and later attribution. |

Numerical gates, task evaluators and authorization controls answer different questions. Their conjunction can support a bounded experiment; no one of them proves all of the others.

## Immediate execution queue and release units

1. **Finish source recovery (#49).** Validate the complete baseline ledger; reconcile full-read findings against the existing summaries. Retain generated inventory, explicit attestation and substantive notes separately. Keep new output review separate from original-source counts.
2. **Land reviewable repairs as independent PRs.** PR #46 worker behavior; PR #47 I4; PR #48 preliminary guidance. Follow with bounded #43 state-contract fixes and #50 widget identity correction. Formal code review remains required; nothing here authorizes a merge or live publish.
3. **P1 contracts in parallel.** #42 I3 semantics/parity, #44 actual local EVM/gateway parity, #45 field provenance, #51 effective-configuration/committed-output/arena ownership, and #52 graph topology/reference semantics. Keep these independently reviewable.
4. **First release unit: local developer and demonstration kit.** Clean environment commands, effective config, known-good fixtures, accessible procedural view, true widget descriptions, hardware/result manifest and replayable example. Separate native runtime and browser recipes. Exit with a second consumer and an actual owner-device record; no new repository is required to reach this point.
5. **Second release unit: one adaptive workspace experiment.** Choose a task using the experiment cards, implement the intent/evaluation contract, compare fixed/heuristic/model or weight-adaptive alternatives, retain rejected candidates and rollback evidence. Do not add every mechanism to the first application.
6. **Parallel research portfolio.** Typed IC/proof correspondence, token-free feedback, learned NCA, preference modeling, OS emulator and RTL simulation each gets a bounded card. Promote evidence-backed branches into implementation; retain inconclusive/negative outcomes without compulsory consolidation.

No finite session can fabricate the future hardware or institutional conditions. The completion obligation for this tranche is complete source accounting, an executable work structure and concrete repairs; the durable queue carries the remaining implementation and research obligations.

## Whitepapers and technical outputs

W1 **models-as-cells** must name the task, cell isolation/lifecycle, baseline-relative guard, fitness/novelty tradeoff, adaptation evidence and failure modes. W2 **graph language** must state the exact node/port/rule system, proof premises and implementation correspondence; a graph hash is not a proof. W3 **provenance/economics** must separate artifact identity, watermark evidence, lineage claims, settlement and token-free alternatives. W4 **organism interface** must connect procedural representations to measurable legibility/accessibility/task outcomes, comparing model effects with heuristics. W5 **constitution versus contract** must enumerate actual authority, mutable guards, consent, appeal and succession, with local contract tests where applicable.
